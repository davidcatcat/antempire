## 怎麼跑（可重現）

```
node prototypes/brood-physiology/bp1-report.ts run <變體>     # 每個變體 20 個種子（1～20），寫 vN/runs/<變體>.json
node prototypes/brood-physiology/bp1-report.ts summarize        # vN/results.json、vN/tables.md
```

- 世界：P0-A2（30 隻工蟻、8 隻幼蟲、一個蜜露情境源、合成天氣 `taichung-march-ref`、參考變體 `ft-flat`），開啟 `WorldOptions.brood`。
- 種子 1～20 與時間長度在執行前就固定：P0-A2 食物 30 日、零供給 35 日、反事實蛋白 40 日。22 個變體 × 20 個種子 = **440 次執行，全部列出**（`vN/tables.md` 的「每個種子」表、`vN/results.json` 的 `per_seed`、`vN/runs/*.json` 的每隻幼蟲）。
- 每次執行每天檢查守恆（工蟻嗉囊、幼蟲換算出去的 µP、食源存量的 µP 帳，加上每隻幼蟲的糖／蛋白／能量整數帳）：v2 **440 次全部守恆**。
- 8 隻幼蟲在 t = 0 是剛孵化的 L1（模型假設；原型沒有齡期資料、沒有蟻后產卵）。巢溫是情境常數（巢溫動態尚未模擬）。

## v1 → v2（#251）：多種子比較

逐變體、逐種子、逐隻比較 `v1/runs` 與 `v2/runs` 的每隻幼蟲欄位（齡期、各階段進入日、餵入糖／蛋白、結構蛋白、糖／蛋白儲備、維持與成長能量、未付維持量、虧損日數、最長虧損段、各限制日數、餵食次數、橋接 µP、死亡原因）：

- **22 個變體 × 20 個種子 × 8 隻＝3 520 隻全部相同**（報告精度：日數 0.01 日、質量整數 ng、能量整數 µJ）。死亡數相同：zs-h1 τ14／τ30 各 160、zs-h2 與 zs-h2-reset 各 153、zs-h3 160，其他 0。
- 日誌雜湊全部不同：每日普查記錄候選版本（`p0a2-bp1/2`），組態雜湊也隨版本改變；這是版本邊界，不是行為差異。
- 為什麼結果不變：#251 的反例需要「本格應付剛好全額付清、維持餘數剛好為 0、期末儲備剛好為 0」連續出現。在這些世界裡，糖只有在「沒有食物」時才用完（零供給：每一格都真的未付），P0-A2 食物與反事實蛋白情境中幼蟲的糖儲備持續累積、幾乎沒有虧損（每變體 160 隻合計 0～3 ng 未付、0.01 日）。所以 v1 的缺陷在現有報告中**沒有改變任何數字**；它能在精確配平的供需下誤判死亡（單元測試的合成邊界輸入，修正前 6 項失敗），v1 的報告結論不需撤回。這不表示其他供給情境不會觸發。

## 死亡原因與用詞（v2）

- `E_deficit`（「維持未付」）只記 v2 定義的虧損格：已累積的維持量沒有被支付或儲備支撐。只是儲備為 0、但本格已全額付清的格點，成長限制記為 `P`（缺蛋白）或 `E_growth`（缺成長能量），不算 `E_deficit`。
- 死亡原因字串 `H1／H2／H3: starvation hazard (research candidate)` 指的是「依 v2 虧損區間累積的缺食危險」（H1：連續虧損滿 τ；H2：本次虧損段的 Weibull 累積危險達到自己的 Exp(1) 抽樣；H3：未付維持量累積達門檻）。H 參數全部是掃描值或測試格點，不是候選值，也不是文獻值。
