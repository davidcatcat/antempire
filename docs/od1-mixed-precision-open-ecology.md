> **文件地位**：設計＋**隔離原型**（`prototypes/mixed-precision/`）。**沒有修改引擎、參數、存檔或正式世界，也不推進遊戲時鐘**（CLAUDE.md §5、§6）。官方流程（`engine/`、`cli/`、`web/src`）不匯入原型，由 `tests/wp5-mixed-precision.test.ts` H 段檢查；規則指紋不含 `prototypes/`。
> **上位文件**：`docs/spec-open-ecology.md`（D7-A 三層架構、邊界事件 §d、驗收 §h）。本文件把其中的 §c.2、§c.5 依 Owner 對 Q1–Q3 的決定改寫成可實作的契約；兩者衝突時以本文件為準（較新、較嚴格），並請 Owner 確認。

## 1. 實體與狀態模型

### 1.1 區域（帳的單位）
| 區域 | 解析度 | 內部位置 | 例 |
|---|---|---|---|
| 花園 | `fine` | 由幾何／物理層（P1-B、`engine/physics/*`）以 cm 表示；**帳只到區域**，花園內移動不是遷入遷出 | `G` 或依 P1-B 切成數個帳區 |
| 外部斑塊 | `coarse` | 只記「在哪個斑塊」＋（若在路上）路段；不追蹤斑塊內座標 | 鄰宅花園、牆腳、行道樹帶（全部是情境假設，`null` 未定） |
| R0 | `coarse` | 有限的都市背景池；外緣封閉（spec §c.3） | — |

### 1.2 個體（individual）
`{ id, taxon, stage, colony_id|null, region, physio{…|null}, comp{區室名: 整數微份} }`
- 焦點蟻群全部成員（工蟻、蟻后、幼體各期、日後的繁殖蟻）恆為個體（Q2、Q3）。
- `comp` 沿用 C2–C5 的區室語意（嗉囊糖、體內蛋白、蟻后體、幼蟲體…）；越界不改。
- 未知生理量是 `null`；升級時從群組來的新個體只有群組記錄過的欄位（spec §c.5.1.4）。原型的群組**不記任何生理欄位**，所以鑄造（匿名成員升級）的個體 `physio={}`（全部未知），不是填入預設值。

### 1.3 群組（cohort）
`{ cohort_id = C|區域|類群|齡期|蟻群, count, comp{合計}, roster[{id, physio}], next_serial }`
- 每個（區域×類群×齡期×所屬蟻群）一組；外部蟻群的成員以 `colony_id` 區分，不併入一般昆蟲（spec I3）。
- `comp` 是全組合計；組內個體差異**不表示**（spec B11；§2.4）。
- `roster` 是已知身分名冊（曾為個體、後來降級者）；`roster.length ≤ count`。

### 1.4 食物存量與去處
- `stock`：場地上的食物（蜜露、花蜜、屍體批次），帶 `origin_event_id`；
- `sink:<名稱>`：離開可食食物池（分解、雨沖）；**不是生物**，不宣稱存在分解者個體；
- `producer:<實體ID>`：只有**活著、被模擬的**生產者（例如寄主上的半翅目群組）可以產生食物；以負值累計，使全世界總量為常數。

### 1.5 表示層級（預設；類群清單本身是情境假設）
| 對象 | 層級 | 依據 |
|---|---|---|
| 焦點蟻群全部成員，不論在花園內外 | 個體，永不降級 | Q2；R116（本種巢間交換靠工蟻移動與交哺，需逐隻） |
| 進入花園並與焦點蟻群接觸的外部蟻群覓食者 | 按需升級，離開且無交互後降級 | Q3；spec §c.2 |
| 獵物昆蟲、被捕食者、在場被照護的半翅目個體 | 按需升級（接觸時） | Q3 |
| 背景昆蟲、半翅目群落、植物族群、外部同種巢 | 群組 | Q3；群組個體（super-individual）是既有建模方法（R340，只核對書目） |

## 2. 升級／降級：觸發與守恆契約

### 2.1 觸發（每一筆都要 `trigger.kind` 與至少一個 `driver_event_ids`，否則拒絕）
| 方向 | 觸發 | 參數 |
|---|---|---|
| 升級 | 與焦點蟻群個體**同時同地**的實際接觸：交哺、捕食或被捕食、搶同一份食物、攻擊、照護 | 接觸半徑、時間窗：沿用物理層的接觸定義；數值為遊戲假設或 `null` |
| 升級 | 宣告為「花園內需個體」的類群越界進入花園（例如大型稀少掠食者） | 類群清單：情境假設 |
| 降級 | **非焦點**個體離開精細格（或回到外部巢），且連續 `demote_after_no_contact_min` 分鐘沒有任何直接交互 | `null`（遊戲假設，未定；需敏感度比較） |
| 禁止 | 焦點蟻群成員降級；在無觸發事件時升級；為畫面或計算量而降級焦點個體 | — |

### 2.2 守恆契約（原型逐筆檢查）
| 契約 | 內容 |
|---|---|
| 數量 | 升級：群組 `count−1`、個體 `+1`；降級相反。兩者**不寫 B/D/I/E**（只是表示改變），同一區域 |
| 質量 | 升級取每個區室的 `floor(合計/count)`；**最後一隻取走全部餘數**（不留下、不捨去）。降級把個體每個區室全數併入群組。每一筆都寫 `food_moves`，獨立稽核重算 |
| 身分 | 升級時以具名亂數 `draw(seed,'promote',key)` 在**全組 count** 中均勻抽一隻：抽中名冊成員就沿用其 ID 與生理快照；抽中匿名成員就**鑄造**新 ID（`identity.action='minted'`；牠本來就在數量裡，不是出生）。降級把 ID 與生理快照寫進名冊 |
| 唯一性 | 任一時刻一個 ID 只在一處（個體或某一名冊）；死亡後退休，永不再出現 |
| 順序 | 名冊依 ID 排序後抽選；指令依（日、分鐘、種類、key）正規排序；與陣列位置無關 |

**與 spec §c.5.1.3 的差異**：spec 建議「優先取用名冊成員」。本設計改為在全組數量中均勻抽選，因為接觸到的是組內任意一隻；優先取名冊會讓曾被觀察過的個體系統性地反覆出現（偏誤）。請 Owner 確認。

### 2.3 越界（Q2）
- `move`：個體從區域 A 到 B，寫 A 的 E 與 B 的 I（同一筆），記 `resolution_change: fine→coarse`；ID、蟻群、生理、區室不變。
- 在外部斑塊時仍可做交哺、取食等 `food_transfer`（接觸仍須同斑塊同時窗；斑塊內接觸機率的模型待定，`null`）。
- `cohort_move`：群組成員跨區，按 §2.2 的方式逐隻取出份額與名冊身分。

### 2.4 已知限制（如實記錄）
- 群組平均化：降級後再升級的個體，拿到的是組內平均份額，不是自己原來的量（測試 C3 明示）。單一成員的組則完全還原（測試 C1）。
- **生理歷史只保留到降級那一刻**：名冊存的是降級時的生理**快照**，在群組期間**不前進**（不增齡、不累積飢餓或發育）；再升級時拿回的是同一份快照（測試 R8 逐 ID 稽核快照未被改動、未被換人）。因此「保留生理狀態」只對焦點蟻群（永不降級）完整成立；對降級過的非焦點個體，群組期間的生理歷史**沒有被模擬**，不得宣稱連續。若需要，群組要有自己的生理分布或名冊快照要隨時間更新，屬未決設計。
- 原型目前沒有任何改變生理的指令，所以稽核要求期末每個 ID 的生理＝重播結果；日後加入發育、老化等指令時，這些變化也必須寫成紀錄，稽核才能重算。
- 若要無損，可改為名冊成員各自保留「份額請求權」；代價是群組的每一次代謝／死亡都要逐名冊成員更新（O(名冊)）。目前不建議，待需要時再議。

## 3. 統一事件帳

### 3.1 紀錄格式（原型 `LedgerRecord`；欄位對應 spec §d.2）
```
{ event_id, kind: birth|death|migration|transport|promote|demote|food_transfer|produce|decay,
  t: { day, minute|null, time_resolution },
  source_region, destination_region,
  identity: { action: born|retired|kept|promoted|minted|demoted|none, ids[], anonymous },
  ledger_effects: [{ region, taxon, stage, colony_id, ledger: B|D|I|E, delta }],
  food_moves: [{ from, to, amount(整數微份), cause }],
  cause: { kind, driver_event_ids[], rule_id, rng_stream, roll },
  resolution_change: { from, to } | null,      // 個體與群組越界都記
  scenario_source: { scenario_id, record_id, source_ref } | null,
  parent: { individual } | { cohort } | null,   // 出生的親代（稽核用）
  cohort_id: string | null }                    // 升降級涉及的群組（稽核用）
```
- 遷入／遷出不是兩筆事件，而是**同一筆**中的 E（來源）＋I（目的）；外緣封閉或 R0 時全世界 ΣI＝ΣE，沒有例外。
- 出生需要同區域活著的親代；新生兒的區室只能從記錄過的區室（例如蟻后體）轉入（spec I6）。
- 生產只能由事件當時**存在且活著、被模擬的**個體或（有成員的）群組進行，並且是**在地的**：生產者、食物存量與紀錄的區域必須相同（模型規則，不是數值；`PRODUCER_REGION_MISMATCH`／`STOCK_REGION_MISMATCH`）。
- 死亡把全部區室轉成同區域的屍體存量，`origin_event_id`＝死亡事件（spec I7）；死因必須是宣告清單中的生物原因（例如衰老、捕食、飢餓），「離開畫面」不是死因（測試 G4）。

### 3.2 獨立稽核（`audit.ts`，不呼叫套用程式）
由「期初狀態＋當日紀錄」重算。第 1–5 項是**平衡恆等式**：必要，但**不充分**——兩隻同類工蟻互換區域、或不存在的「生產者」記一筆負帳，總數與總量照樣閉合（Codex R13-03、R13-04）。所以還有第 6–8 項的逐筆重播。
1. 每個區域×類群×齡期×蟻群：期末＝期初＋B−D＋I−E；
2. 每個區室：期末＝期初＋流入−流出；全世界總量不變（生產記在生產者的負帳）；
3. 身分：期末 ID＝期初＋出生＋鑄造−退休；一處一 ID；名冊 ≤ 數量；退休者不復活；
4. 紀錄形狀：出生只有一個 B、死亡只有一個 D、遷移的 I 與 E 成對、升降級不改數量、遷移只帶群組份額、死亡的食物只進屍體存量、生產只來自生產者、搬運必須對應已登錄且未用過的情境紀錄；
5. 焦點蟻群成員不得出現在任何群組；
6. **逐筆重播**（依（日、分鐘、種類、key）正規順序，不信任輸入順序）：重建每個 ID 在哪個區域、是個體還是哪個群組的名冊成員、生理快照；每筆越界的來源、目的、E/I、身分（個體或名冊 ID＋匿名數）、`resolution_change` 與食物移動都必須和重播當時的狀態一致；搬運的對象必須是情境紀錄寫的那一隻或那一組；升級只能取該群組名冊上的 ID 或鑄造新 ID，降級只能把個體放進自己的（區域×類群×齡期×蟻群）群組；
7. **來源合法**：每筆 `produce` 的生產者在事件當時必須存在、是被模擬的個體或有成員的群組、未退休，且與存量同區域（不存在／已退休／當日稍早死亡／群組已空 → 違規）；每筆出生的親代在當時活著且同區域；每筆食物的來源區室在事件前存在、去處在事件後存在；新存量只能由生產或死亡（屍體）建立，區域與 `origin_event_id` 要對得上；
8. 期末逐 ID 比對：區域、類群、齡期、蟻群、生理、名冊成員與名冊快照、存量的區域與來源都要等於重播結果。

**仍然保證不了的**：稽核只能檢查紀錄彼此及與狀態是否一致，不能判斷觸發原因（`cause`）在生物上是否真的發生、情境紀錄的 `source_ref` 品質（§9.1 第 4 項），也不能判斷死因是否屬於宣告清單以外的「離開畫面」（測試 G4 以另一條規則檢查）。

## 5. Issue #80：食源損失與分解的守恆候選（`prototypes/mixed-precision/decay.ts`）

**式**（每個存量、每一步，整數）：
```
S1      = S + Σ 來源（新屍體、分泌…，每筆帶來源 ID）
sink_k  = floor(S1 × num_k / den_k)     （所有去處同時由 S1 計算，Σ 比率 ≤ 1）
S'      = S1 − Σ sink_k
若 0 < S' < clear_below：再記一筆 remainder_cleared → sink:decomposition，S' = 0
檢查：S' − S = Σ來源 − Σ去處（逐筆、精確）
```
- **沒有到期刪除**：舊模型第 9 日刪除仍有可食量的屍體（`docs/design-source-flows-v26.md` §5、登錄表 ECO-CARC-EXPIRE）；本候選只允許有紀錄的去處。
- 去處只能是：分解（離開可食池，不宣稱分解者個體）、具名的物理流失（雨沖），或**已被模擬**的消費者（以 `food_transfer` 進其區室）。不得為了有去處而捏造腐食者族群。
- 比率、門檻：**遊戲假設**（沿用現行 0.14／日＋雨加成是遊戲假設；本原型不設值）。屍體在地表很快被取走、落葉層內可存在整年是他地研究（R187、R188，非本地）的方向，只能作情境比較。
- 與 v26 的關係：v26 只把現行浮點算式寫成事件（存量不變）；本候選改為整數有理比率、無到期刪除，**會改變供應量**，屬規則更新，需 Owner 先決定屍體到期的矛盾（v26 §5 方案 A／B）。

### 7.2 估計（遊戲假設：工作量）
- **每隻焦點個體每日約 20 筆事件**（取自現行引擎平均）；P0-A 24 小時與物理層接上後會增加，倍數 `null`（待量測）。
- **背景**：群組數＝斑塊×類群×齡期（例 12×6×3＝216 到 50×10×4＝2,000）；每組每日約 3–5 筆（出生、死亡、擴散到每個鄰接斑塊）。群組的成本與其內含個體數**無關**。
- **升級**：與接觸次數成正比；上限是焦點個體的接觸事件數。
- **漸近**：帳本身 O(E log E)／日（正規排序）＋稽核 O(E log E＋狀態)（重播也排序；原型檢查新 ID 唯一時逐一掃描名冊，鑄造／個體出生多時要加索引）。真正的瓶頸是**接觸偵測**：若逐對比對為 O(n²)，必須用空間索引（物理層已有格網）降為約 O(n)。
- **結論（程式層面）**：1000 隻焦點蟻群＋2,000 背景群組，帳與稽核每日約 0.15 秒；生物子模型（現行引擎 1000 隻約 0.1 秒／日，未含 24 小時與物理）才是主要成本。多年（3,650 日）×多種子的批次可行，但 10⁴ 隻以上的焦點蟻群需先量測接觸偵測。
