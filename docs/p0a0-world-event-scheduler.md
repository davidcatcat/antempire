# P0-A0：共用世界事件排程器（工程基礎）

> **地位**：P0-A（24 小時生態時鐘）的**工程基礎**。**不是** 24 小時生態行為，也沒有完成 P0-A。
> - 沒有接入每日模擬：`simulateWorldDay()`、`cli/`、`web/src` 都不引用它（`tests/scheduler-isolation.test.ts`）。
> - 不在規則指紋內：指紋只涵蓋 `engine/*.ts`（`cli/lib/fingerprint.ts`）。
> - 既有引擎輸出逐位元組不變，正式存檔、Day1～14、Day15 都沒有改動。
> - 沒有生物參數、沒有行為、不抽亂數。
>
> **時間契約（Owner 審查 #116 後補充）**：見 [`p0a0-time-contract.md`](p0a0-time-contract.md)。每個事件現在保留原生時間與精確時刻；本文的 60 µs 格點規則是其中的 `tick` 契約（預設），同格合併一律偵測並回報，或用 `on_conflict: 'refuse'` 拒絕；另有 `layered` 契約依精確時刻排序。快照格式改為 v2。
>
> **程式**：`engine/scheduler/world-events.ts`
> **測試**：`tests/p0a0-world-scheduler.test.ts`（208 項）、`tests/scheduler-isolation.test.ts`
> **依據**：`docs/research-design-p0a-24h-clock.md` §2.1、§3；`docs/multi-colony-timeline.md`（A09、#9）；`docs/roadmap.md` 的 P0-A／A09。

## 1. 為什麼要有共用排程器
目前 `engine/` 裡有三套各自的事件順序：

| 位置 | 排序鍵 | 問題 |
|---|---|---|
| `engine/activity.ts`（v17 個體活動時間軸） | 時間 → 事件種類等級 → 工蟻 ID → **插入順序** | 平手時退回插入順序（FIFO）；兩處就地改時間後重新排序；佇列不跨日 |
| `engine/foraging.ts`（屍體地點的捕獵時鐘） | 最早抵達 → 地點 ID → 工蟻 ID | 只用於捕獵地點 |
| `engine/physics/collision.ts`（隔離物理） | 候選最小時刻 → 事件種類等級 → 個體 | 秒制、隔離層 |

另外，`prototypes/multi-colony-timeline/timeline.ts` 示範了「所有蟻群的抵達放進同一個時鐘」（#9），但它是原型，裡面的按比例分配規則是**佔位規則**，不是生物學。

24 小時生態、個體運動、多蟻群競爭、捕食與局部接觸，都需要**同一個**世界時鐘。若各自再寫一套，就會有第四套順序。

### 本 PR 的重用決定
- **重用的是規則，不是程式碼**：
  - 「時間優先、事件可以跨日、不在 24:00 重設」來自 P0-A 設計 §2.1；
  - 「同一時刻的所有事件一起處理，與陣列位置無關」來自 #9 的時間窗；
  - 「排在過去就拒絕」來自 `activity.ts` 的 `push`。
- **沒有改寫 `activity.ts`**：它的 FIFO 平手規則會影響亂數抽取順序，改成新排程器就會改變輸出，那是規則更新，不屬於本 PR。
- **沒有引用物理層**：`kinematics.ts` 的 `orderEvents` 是可重用的比較函數，但物理層必須保持隔離。
- 以後的整合順序見 §6。新排程器是這三套的**匯合點**，不是第四套。

## 2. 事件介面
| 欄位 | 內容 |
|---|---|
| `at` | 世界時間 `{day, minute}`：day 為 ≥ 0 的整數；minute ∈ [0, 1440)，臺灣標準時間，00:00 = 0。minute 可以是小數，但一律對齊到固定格點 `TICKS_PER_MINUTE = 10⁶`（10⁻⁶ 分鐘 = 60 µs，與引擎 `round()` 的格點相同；這是工程選擇）。同一時刻＝格點整數相等，所以 0.1 + 0.2 與 0.3 是同一時刻。這是唯一的正規化：小於半個格點的分鐘或延遲會變成 0（子事件因此落在同一時刻的下一輪）。會進位成 24:00 的分鐘要寫成次日 0，否則拒絕 |
| `scope` | 事件屬於誰：`{world, colony, individual}`；不屬於某蟻群或某個體時填 `null`。個體必須屬於某蟻群 |
| `source`、`target` | 來源與目標（同樣格式，可為 `null`） |
| `kind` | 事件種類（小寫識別字）。排程器**不**給種類任何優先順序 |
| `key` | 生產者提供的鍵，必須來自實體 ID，不得來自陣列位置 |
| `id` | **標準識別**：根事件是 `kind:key`，子事件是 `原因id/kind:key`。由內容決定，與插入順序無關；重複就拒絕 |
| `cause` | 造成它的事件 id（根事件為 `null`） |
| `round` | 同一時刻內的因果深度：子事件與原因同一時刻時，排在下一輪 |
| `state` | `scheduled` → `executed` 或 `cancelled`，只有這兩種轉換 |
| `payload` | 純 JSON 資料：會複製、依鍵排序並凍結；拒絕 NaN、Infinity、函式、Date 等 |

## 3. 處理規則
1. **順序**：依 `(day, 格點, round, id)`。這是事件本身的純函數；不依 `colonies[]`、`workers[]` 的位置，也不依插入順序。
2. **同時事件**：同一時刻、同一輪的所有事件組成**一批**，一起交給處理函式。
   - 批內依 id 排列，只為了紀錄可重現；
   - 排程器**不決定**同時事件誰先、誰得到資源。交哺、攻擊、採集、讓路等同時競爭的規則還沒有決定，本 PR **不實作**；
   - 處理函式必須把一批當成集合處理；
   - 排程器不接受任何優先順序欄位（多出的欄位會被拒絕）。
3. **因果**：
   - 不得排在原因之前，也不得排在目前時鐘之前；
   - 與原因同一時刻的子事件在下一輪執行；
   - 一批不能取消同一批中的事件，因為那等於私下決定同時競爭的結果；
   - 世界輸入（根事件）不得加在已在處理中的時刻，只能排在之後。否則它會被默默排在同時刻事件之後的一輪，等於由「何時被排入」決定先後；
   - 處理函式執行中，以及排程器讀取、複製、驗證其輸出期間（含 getter、Proxy trap、`toString`），都不得呼叫 `schedule`、`cancel`、`step`、`runUntil`、`runDay`、`snapshot`（拒絕重入）。`schedule`／`cancel`／`runUntil` 讀取呼叫者物件時同樣持有排程器。保護在 `finally` 中解除，失敗時狀態完全不變。只能讀取，讀到的是凍結的複本；
   - `get`、`pending`、`log` 與交給處理函式的事件都是凍結的深複本，外部改不到內部狀態。
4. **原子性**：處理函式的輸出全部驗證通過才套用。驗證失敗或處理函式丟出錯誤時，狀態完全不變，那一批仍待處理。
   - 排程器之外的狀態（例：環境時鐘）可用 `setCommitHook` 與該批一起提交：鉤子在輸出驗證通過之後、排程器提交之前被呼叫，收到該批排序後的 ID 與處理函式；鉤子丟錯時該批退回、排程器不變。鉤子不在快照中，還原後由持有者重新設定（Codex R13-02）。
   - **只讀一次**（Owner P2，2026-11-07 更正）：前一版先讀輸出來驗證、提交時再讀一次。輸出若帶 getter 或是 Proxy，兩次讀到的值可以不同：驗證通過，提交時才失敗，批次卻已標為已執行（部分提交）；或者驗證的是合法值，存進去的卻是另一個值。
   - 現在處理函式的輸出與 `schedule()` 的事件規格，每個欄位都**只讀一次**，複製成純資料；驗證與提交都只用這份複本。提交階段不再讀取任何生產者物件，也不會失敗。
   - **輸出的形狀**（子代理審查，非 Codex）：處理函式只能回傳 `undefined` 或純物件 `{children?, cancel?}`。Promise（非同步處理函式）、拼錯或多餘的欄位（含不可列舉、Symbol 鍵）一律拒絕，不再被當成空輸出而讓子事件遺失。子事件只能有 `cause, spec`，取消只能有 `id, reason`。
   - payload：明寫的 `undefined` 視為沒有 payload（`null`）；名為 `__proto__` 的鍵保留為一般鍵；不可列舉的欄位會讀到；陣列有空洞時拒絕。
   - 工程上限（不是模型參數）：每個 payload 最多 `MAX_PAYLOAD_NODES = 100,000` 個值，每份輸出最多 `MAX_OUTPUT_ITEMS = 100,000` 項。超過時迅速拒絕，不會先跑完巨大的迴圈。
5. **跨日**：
   - `addMinutes` 跨越午夜時進位到下一日；
   - `runDay(d)` 只處理第 d 日的事件，之後日期的事件留在佇列中，**不在 24:00 重設**；
   - 處理完的那一日即關閉：之後不得再把世界輸入排在該日或更早，也不得重跑該日；
   - 必須依序處理各日；
   - `snapshot()`／`restore()` 讓佇列可以跨存檔延續；
   - 還原時拒絕任何不一致的快照：欄位集合不對、種類或鍵非法、時間不在格點上、round 不是整數或與原因不一致、原因不存在或未執行、子事件早於原因、已執行的事件晚於時鐘、待處理的事件不在時鐘之後、取消欄位與狀態不符、`log_seq` 小於已完成事件數。
6. **恰好一次**：每個事件最後是已執行、已取消或待處理三者之一，不會兩者兼有、不會重複、不會遺失。
   - `audit()` 檢查這一點，並把還原前已完成的事件分開計數；
   - `verifyLog()` 獨立檢查執行紀錄的順序與因果，不信任排程器的內部狀態；還原後的紀錄只要附上快照的事件，就可以單獨驗證；
   - `runUntil` 的每一批是原子的，整段執行則不是：超過批數上限時，在已完成的批次之後停下，狀態一致。

## 4. 本 PR 不做的事（需要另外的生物參數或 Owner 決策）
- 任何行為：喚醒、休息、覓食、交哺、接觸、攻擊、讓路、捕食。
- 同時事件的競爭規則：例如 #9 原型的按比例分配，仍是待決定的佔位規則。
- 環境：逐分鐘溫濕度、降雨事件（P0-A 設計 §7）。
- 亂數流：排程器不抽亂數。測試中的亂數只用於產生合成事件，依「種子＋事件 id」取流，與處理順序無關。這是給未來整合的建議做法，不是已核准的規則。
- 接入每日模擬、存檔格式、觀察器。

## 5. 驗證（`tests/p0a0-world-scheduler.test.ts`）
測試用的事件產生器是**測試工具**：延遲時間與事件種類都是合成的，不是生物學主張。

| 要求 | 測試 |
|---|---|
| 相同輸入與種子 → 完全相同 | 執行紀錄與快照逐字相同；換種子會不同（確認比較有效） |
| 調換陣列順序不變 | 20 種排列：同時打亂 `colonies[]`、`workers[]`、根事件的排程順序與處理函式的輸出順序，紀錄與快照逐字相同 |
| 對照組 | 依插入順序平手的佇列（`activity.ts` 的做法）在 `colonies[]` 反轉時會改變，證明測試能抓到順序依賴 |
| 不在因果時間之前執行 | 每次都跑 `verifyLog`；排在原因或時鐘之前、取消自己這一批的事件、原因不在本批，都被拒絕；調換兩筆紀錄、或刪掉原因的紀錄，`verifyLog` 都拒絕 |
| 跨日不重設 | 23:59.75 的事件排出 30 分鐘後的子事件，留到第 1 日執行；逐日處理並在每日之間快照／還原，與連續處理逐字相同；跳日處理被拒絕 |
| 不重複、不遺失 | 總數 = 已執行 + 已取消 + 待處理；沒有 id 出現兩次；已取消的不執行；無效輸出或處理函式丟出錯誤時狀態不變 |
| 子代理審查的發現（Claude 子代理審查，非 Codex） | 處理函式中重入被拒絕且狀態不變；回傳與交給處理函式的物件都凍結；0.1 + 0.2 與 0.3 同批；延遲的分組方式不影響時刻；會進位成 24:00 的分鐘被拒絕；已處理時刻的世界輸入被拒絕；24:00 屬於次日；失控排程在 50 批停下且一致；還原後的紀錄附上快照可單獨驗證；同時刻子事件 round 被竄改時 `verifyLog` 拒絕；12 種不一致的快照都被拒絕 |
| Codex R9-01／R10 §4：讀取輸出期間重入 | 輸出 getter 取消其他事件後丟錯：被拒絕，兩事件仍為待執行，快照與紀錄不變；getter 排更早的根事件：被拒絕，時鐘不倒退；8 種讀取路徑（getter、陣列索引 getter、spec／payload getter、`toString`、Proxy ownKeys／get）× 6 種變更 API 全部拒絕且狀態不變；吞掉拒絕後回傳合法輸出時只提交本批；`schedule`／`cancel`／`runUntil` 讀取呼叫者物件時也拒絕重入；保護一定解除。此組測試在修正前的程式上失敗 |
| 非法輸入被拒絕 | 時間：負日、小數日、minute = 1440、負值、NaN、Infinity、超出安全整數；非法種類與鍵；他世界的參照；沒有蟻群的個體；多餘欄位；非 JSON 的 payload；優先順序欄位；取消已執行、已取消或不存在的事件；重用 id；篡改的快照 |
