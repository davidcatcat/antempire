# P0-A0：世界時間與物理時間的單位契約

> **地位**：回應 Owner 對 #116 的審查。仍是**隔離的工程基礎**：沒有接入每日模擬、不在規則指紋內、不推進遊戲日、沒有生物參數。
> **程式**：`engine/scheduler/world-events.ts`（原生時間、精確時刻、兩種排序契約、偵測）、`engine/scheduler/time-contract.ts`（候選契約的量測核心）、`prototypes/p0a0-time-contract/measure.ts`（產生本文數值表）。
> **測試**：`tests/p0a0-time-contract.test.ts`（阻擋性）。本文第 5 節的三張數值表由測試重新計算，必須與本文**逐字相同**。
> **最後選擇由 Owner 決定**；程式預設仍是 #116 的 `tick` 契約（加上偵測），`layered` 需要明確指定。

## 1. 問題
#116 把每個時間對齊到 60 µs 的格點（10⁻⁶ 分鐘）。同一格內的事件被當成「同一時刻」放進一批。
- 兩個相距不到 60 µs 的真實事件（接觸、進出、交哺候選）會被合併，處理函式只看到一個集合，原本的先後順序消失。
- 以本種路徑速度 17 mm/s（R133，文獻支持；只用來換算距離）計算，60 µs ≈ 0.00102 mm。這是**誤差的尺度**，不是可以接受的容許值：物理層本來就分得出這些事件的先後。
- 物理層（`engine/physics/collision.ts`，PH-2）用連續的秒。本分支的 PH-2 以 `T_EPS = 1e-9 s` 當數值容許；其他物理分支（ph-p2d、ph3a-2d）用 `SAME_INSTANT = 16 ulps`。同一時刻的事件在物理層內就已經用同一個 `t_s` 送出。

## 2. 名詞
| 名稱 | 意義 |
|---|---|
| 原生時間 `native` | 生產者自己的時間：`{clock, unit, anchor, t}`。`clock` 是具名時鐘（例如 `ph2.colA.run17`），`unit` 是 `'s'` 或 `'min'`，`anchor` 是 `t = 0` 對應的世界時刻（必須在格點上），`t` ≥ 0。只給 `at` 的事件，原生時間是 `{clock: 'world', unit: 'min', anchor: 當日 00:00, t: 分鐘}` |
| 精確時刻 `exact` | 原生時間換算成「某日 00:00 之後的微秒」，以兩個 double 的未求值和 `us + us_lo` 保存（無誤差乘法 TwoProduct、無誤差加法 TwoSum）。兩個不同的原生值不會因換算而變成相等 |
| 世界刻 `at` | 精確時刻最接近的 60 µs 格點（正好一半時進位）。在 `layered` 契約中只是**標籤** |
| 批次 | 一起交給處理函式的事件集合 |

每個事件同時記錄 `native`（原值，逐位元相同）、`exact` 與 `at`。還原快照時重新計算，三者不一致就拒絕。

## 3. 契約條文（兩種契約共同）
1. **捨入不得修補或重排真實的順序。** 兩個原生時間不同的事件若落進同一格，必須**被偵測並回報**，或由分層排序分開；**絕不默默合併**。
2. 排程器**不加任何容許值**，也不判斷兩個事件「其實是同一時刻」。同一時刻由生產者決定：物理層在自己內部用自己的規則（`T_EPS`／`SAME_INSTANT`）把同一時刻的事件送出成同一個 `t_s`。排程器只把**完全相同**的精確時刻視為同時。
3. 延遲必須在原生時鐘上相加（`addNative`），不得在格點上相加。舊的 `addMinutes` 先把延遲單獨捨入，誤差可達 1 格，還會讓子事件排到真正較早的事件之前（§6 反例 4），而且因為真實時間沒有交給排程器，**排程器無從偵測**。
4. 真正同時（精確時刻相同）的事件仍是**一批**，排程器**不決定**誰先、誰得到資源（§8）。

### 3.1 `tick`（#116 契約＋偵測）
- 排序：`(日, 格, round, id)`。同格的不同精確時刻會被合併成一批。
- 每一次合併都記錄在 `timeReport().merges`（不同時刻數、時間跨度），處理函式也從 `ctx.distinct_instants` 得知。
- 一批中若有事件的精確時刻**早於**已執行的事件（順序被改變），記錄在 `timeReport().inversions`。
- `on_conflict: 'refuse'`：遇到合併或反序時，在處理函式執行前拒絕，狀態不變。
- 會捨入成 24:00 的時刻一律拒絕（#116 規則）。

### 3.2 `layered`（分層時間）
- 排序：`(精確時刻, round, id)`；世界刻只是標籤。
- 一批＝同一精確時刻、同一 round 的事件。不同原生時刻**不會**同批，順序就是精確時刻的順序。
- 子事件不得早於原因的精確時刻；與原因同一精確時刻才進入下一 round。
- 世界輸入不得落在已處理的精確時刻或更早。
- 日界由精確時刻決定：午夜前最後半格的事件仍屬當日，標籤留在當日最後一格（誤差 < 60 µs），不會被移到次日。
- 在這個契約下，偵測器若發現合併或反序，代表程式錯誤，會直接拒絕。

## 4. 量化誤差界與出處（要求 1）
| 步驟 | 誤差界 | 測試 |
|---|---|---|
| 分鐘 → 格（`checkTime`） | 對**實數值**正確捨入：\|格 − 分鐘×10⁶\| ≤ 0.5 格 = 30 µs，正好一半進位 | 0.09375 s = 1562.5 格 → 1563；小 1 ulp → 1562；大 1 ulp → 1563 |
| 原生 → 精確時刻（`exactOf`） | 乘法與加法無誤差；只有低位相加會捨入，相對誤差約 2⁻¹⁰³（在 1 日內約 10⁻²⁰ µs） | t = 1000 s 與大 1 ulp 的值：直接換算成分鐘時相等，精確時刻仍分得開；隨機 2000 對單調 |
| 精確時刻 → 世界刻（`labelOf`） | \|標籤 − 原生時間\| ≤ 30 µs；`layered` 只有午夜前最後半格 < 60 µs | 兩種契約各 4000 個隨機原生時間（兩種單位、隨機錨點、5 個時鐘；會捨入成 24:00 的略過）：最大 30 µs 以內，且每個標籤等於獨立計算的最近格 |
| 可表示範圍 | `t × 單位微秒數 < 2⁵¹`（秒約 2.25×10⁹ s，分鐘約 3.75×10⁷ min）；超出拒絕 | 超出範圍、負值、錨點不在格點上、多餘欄位都拒絕 |

**與 #116 的差異（刻意的契約變更）**：#116 用 `Math.round(分鐘 × 10⁶)`，對**浮點乘積**捨入。例如 `5e-7` 分鐘在二進位是 0.49999999999999998 格，舊規則得 1，新規則得 0。新規則的誤差界對真實數值成立。#116 的 208 項測試全部不變地通過。

## 5. 候選契約的數值比較（要求 3）
資料：
- **真實 PH-2 事件序列**：`tests/ph2-collision.test.ts` 的合成場景（迎面、交叉、單行三隻、巢口帶 3 mm 負載、雙向交通 8 隻 × 12 種子、擁擠走廊 25 種子），每次執行一個原生時鐘，錨點 10:00。遭遇規則是候選規則，不是已驗證的螞蟻行為；這裡只用事件**時間**。
- **合成的近同時事件對**：每種間隔 1000 對，基準時刻在 [0, 1000) s 均勻抽取，哪一個拿到較小的 id 也隨機。

指標：
- **合併對**：精確時刻不同、卻被放進同一批的事件對（順序遺失）。
- **同個體**：其中兩事件涉及同一隻工蟻的對數（例如同一隻的 `yield_resume → obstruction → follow_start` 連鎖）。
- **id 反序**：合併對中 id 順序與真實時間順序相反的對數。若使用者像 `activity.ts` 處理平手那樣依 id 走過一批，就會以錯誤的因果順序處理。

## 6. 反例回歸（要求 2，`tests/p0a0-time-contract.test.ts`）
1. **± 半格**：相距 29 µs 的兩事件在 `tick` 同批，而相距 2 ulp（約 3×10⁻¹⁷ s）、跨過半格的兩事件卻分屬兩批。距離越近不一定越「同時」，這是格點造成的。`tick` 回報這次合併（3 個不同時刻，跨度 29.4 µs）；`refuse` 拒絕且狀態不變；`layered` 給出 4 批，依精確順序。
2. **午夜**：午夜前 15 µs 的事件：`tick` 拒絕（不會被移到次日）；`layered` 留在第 0 日。PH-2 交通執行錨定在 23:59:45、跨越午夜，含以 `addNative` 跨日的子事件：兩種契約下，逐日處理加快照／還原都等於連續處理；每個事件恰好一次；`verifyLog` 通過。
3. **同一時刻很多事件**：1000 個相同原生時刻的事件在兩種契約都是一批，不算合併。1000 個落在同一格的不同時刻：`tick` 一批，處理函式與報告都標示 1000 個不同時刻；`layered` 依精確順序分成 1000 批（反序排入也一樣）。
4. **改變步長**：
   - 延遲分組：原因在 0.4 格，另一事件 x 在 0.7 格，子事件延遲 0.4 格。用 `addMinutes` 時，子事件（真實 0.8 格）排在 x 之前，而且無法偵測。改用 `addNative`：`tick` 把子事件與 x 合併並回報；`layered` 給出正確的「原因 < x < 子事件」。
   - 子事件的精確時刻早於原因、但同格：`tick` 依 #116 規則接受，執行時被偵測為反序（早 12 µs）；`layered` 拒絕。
   - 物理的廣域相位視窗 `window_s` ∈ {0.05, 0.5, 7}：在 122 次可比較的執行中，99 次的事件時間逐位元不同（最多約 7×10⁻¹³ s），但四種契約的批次結構全部相同。
5. **種子／id／輸入順序不變**：PH-2 交通事件以 20 種隨機排入順序加上隨機改名的 id 排入。兩種契約的批次（以原生時刻集合表示）都不變。`layered` 連「依 id 走過一批」的順序都不變，因為一批只有一個時刻。對照組：`tick` 下依 id 走過合併批次的順序，在改名後 20/20 都改變——順序取決於名字，不是時間。

## 7. 推薦（最後由 Owner 決定）
**推薦 `layered`**（世界刻做標籤與分日，精確原生時刻做排序）：
1. 唯一在所有真實 PH-2 序列與所有合成間隔上都**不合併、不反序**的契約；不依賴格寬，也就不需要為格寬再做一次決定。
2. 保留出處：每個事件帶原生時間，誤差界可以逐事件檢查與重算。
3. 成本與 `tick` 相同（§5.4）。
4. 日界、跨日、快照／還原、多蟻群、id／順序不變性都已測試（§6、§8）。

其他選項：
- `tick` + `on_conflict: 'refuse'`：保證不默默合併，但在 PH-2 交通場景中幾乎每次都會拒絕（12 次執行有 721 對合併），等於無法使用物理事件。
- 更細的整數格（1 µs、1 ns、0.1 ns）：仍會合併（1 ns 有 29 對），沒有安全邊際；1 ps 已無法以整數表示。
- 維持 `tick` + 回報：只適合事件本身就以分鐘為單位、且不需要格內順序的生產者。

## 8. Owner 清單的其他項目
- **真正同時的事件**：精確時刻相同的事件是一批，排程器不決定競爭結果（一批不能取消自己的事件、不接受優先順序欄位）。同時競爭的規則（交哺、採集、讓路等）**仍是開放問題，需要 Owner 決定或文獻**；本 PR 沒有發明任何規則。
- **跨時鐘的「同一時刻」**：0.5 min 與 30 s 是同一精確時刻（測試確認一批、不算合併）。但 0.025 min 在二進位不等於 1.5 s，精確時刻相差約 8×10⁻¹¹ µs，`layered` 會把它們分開。排程器無法知道生產者的意圖。是否要求生產者用同一個值表示同一時刻（例如用二進位可表示的值，或同一時鐘），由 Owner 決定。
- **日界**：不重複、不遺失、可跨日重播（§6 反例 2）。
- **多蟻群共用世界時間**：蟻群 A 的秒時鐘與蟻群 B 的分鐘時鐘（不同錨點）在同一排程器中，依精確世界時刻交錯，與排入順序無關（測試）。
- **穩定 id 與具名亂數流**：
  - 事件 id 是標準 id（`原因id/kind:key`），key 必須來自實體 ID，例如物理事件用 `種類.個體.對象.第幾次`。
  - **排程器本身不抽亂數。** 生產者為某個事件抽亂數時，亂數流名稱為 `rngStreamName(world, 事件 id, 用途)` = `rng/<世界>/<事件 id>#<用途>`，種子為 `hash32(種子|名稱)`。這樣抽到的值只取決於內容，與處理順序無關（測試）。這是給整合者的**建議命名**，不是已核准的規則。
- **時間精度敏感度**：§5.2（9 種格寬 × 8 個相位）與 §5.3。
