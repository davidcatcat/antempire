# C4 幼蟲營養因果鏈分析（2026-11-07，只報告）

> **地位**：報告，不是規則更新。**不改引擎、不改參數、不打開任何開關**（物種檔所有開關照舊關閉，C4b 形式照舊未選）。不推進遊戲日、不改 Day1～14 歷史與 Day14 權威存檔、不啟動新版正式 Day0。

## 1. 起因

Owner 由 #114 診斷看到三件事同時發生：

- 68.3 % 的幼蟲日沒有任何餵食接觸；
- 幼蟲蛋白攝取只有需求的 19.4 %；
- 同時巢內蛋白大量溢出。

本報告**不提高餵食頻率、不改任何參數**，只把「食物從哪來、在哪一關停下」逐關記錄下來。

## 3. 守恆（數學不變量）

- 每個群體日、每個追蹤區室（in_transit、crop 糖／液態蛋白、cache、nest_unlocated、queen_body、larva_body），**彙總與逐個體**都檢查：期初（開始狀態）＋流入（food_transfer）＝流出＋期末（結束狀態）。
- 結果：80,871 個區室日、243,615 個個體區室日，**最大殘差 0，失敗 0**（容差 2×10⁻⁵）。
- 每個世界另檢查：採集＝卸貨（帶回途中沒有損失）；`feed_larva`＝幼蟲攝取；工蟻嗉囊交出的蛋白不超過取得的量；每個幼蟲日恰屬一類。
- 限制：世界食物源的生長與衰退不是 food_transfer，由引擎的 `checkSources` 另行封閉，本報告不重做。

## 5. 分析

### 5.1 為什麼存放的食物到不了幼蟲【推導】

1. **不是採集不足，也不是存量不足**：cache 幾乎每天都夠；溢出大於幼蟲總需求。
2. **結構上限**：每隻保育工蟻每日只接觸 1 隻幼蟲、每次最多一口（0.08 份，剛好等於參考溫度下一隻幼蟲一日的需求）。所以就算每次接觸都達門檻又都帶蛋白，可送達量最多只有幼蟲需求的 **41.8 %**（`one_contact_one_bolus_ceiling_over_larval_need`）。實際的 19.4 % 是在這個上限之下再打折。
3. **人數**：平均每日 1.33 隻保育工蟻；38.7 % 的群體日沒有任何保育工蟻（28.5 % 的幼蟲日因此直接斷鏈）。
4. **取用與嗉囊**：工蟻取蛋白每回合最多 0.28 份，且與糖共用嗉囊（0.8 份）。581 個保育工蟻日因嗉囊被糖裝滿而取不到蛋白。
5. **蟻后段在前**：回合順序是 store → 蟻后 → 幼蟲。工蟻先在蟻后處最多交出 0.28 份；253 個工蟻日把取得的蛋白全給了蟻后。
6. **放回**：一口之後剩下的液態蛋白在回合結束放回 cache（嗉囊不過夜），所以「多拿」不會變成「多餵」。
7. **溢出**：放回與未取用的蛋白留在 cache，超過容量（12＋每多一隻工蟻 0.3 份）的部分每日以 `storage_overflow` 損失。

### 5.2 接觸機制是否過度簡化【推導】

是。以下都是程式中的固定次數或上限，**全部是遊戲假設，沒有本種數據**：

| 程式位置 | 內容 | 類型 |
|---|---|---|
| `engine/day.ts:170` | 每群每日只有一個巢內回合，是食物到達幼蟲的唯一途徑 | 固定次數 |
| `engine/queen-feeding.ts:76` | 只有任務為 nurse 且 `last_location` 在巢的工蟻參加 | 資格 |
| `engine/queen-feeding.ts:83` | 每隻每回合最多取 0.28 份，受嗉囊剩餘空間限制 | 每日上限 |
| `engine/queen-feeding.ts:247` | 引擎檢查強制「每回合只取一次」 | 固定次數 |
| `engine/queen-feeding.ts:100`、`:117` | 蟻后段（每接觸最多 0.28 份）在幼蟲段之前 | 順序 |
| `engine/larva-feeding.ts:114` | 每隻保育工蟻每回合恰好抽 1 隻幼蟲 | 每日上限 |
| `engine/larva-feeding.ts:120` | 每次接觸每種食物最多一口（蛋白 0.08＝幼蟲日需求） | 每次上限 |
| `engine/larva-feeding.ts:44` | 需求隨 Q10 代謝係數變大，一口份量固定：高於參考溫度時一口餵不飽（246 個餵到的幼蟲日需求大於一口） | 不一致 |
| `engine/queen-feeding.ts:124` | 回合結束剩下的液態蛋白放回 | 規則 |

- 「一日一回合、一工蟻一接觸、一接觸一口」三者相乘，構成 41.8 % 的上限。這是模型結構，不是生物結論。
- 保育工蟻整天在巢內（一日一任務），卻只做一次接觸；真實的照護是持續的時間預算，本種沒有接觸頻率資料（`null`）。

### 5.3 保育工蟻怎麼選工作【觀測＋推導】

- `engine/foraging.ts:431`：每隻工蟻**每天重新抽一次**任務，沒有持續性。
- `engine/workers.ts:48`：保育權重 0.25 ×（1 + 0.65 × 自己的求食線索）× 新生倍率；全部是遊戲假設。
- `engine/workers.ts:96`：求食**線索**接觸（機率 0.75）是另一次獨立抽樣，不是餵食接觸；給線索的幼蟲不一定是被餵的幼蟲（兩套接觸系統）。
- 輸入都是工蟻自己的嗉囊、自己接觸到的同伴與幼蟲；**沒有讀全巢總量**（§5.5）。
- 小蟻群（約 5～15 隻）用每日抽籤，常常整天沒有保育工蟻。本種沒有任務分配或年齡分工的一手研究（`docs/references.md`：「查無本種任務分配、年齡分工……的一手研究」）。

### 5.4 代謝、發育與死亡斷開【觀測】（已知缺陷 L2／L3，C4c 待做）

- `engine/nutrition.ts:81`：C4a 打開時，全巢蛋白比例不再計入幼蟲（`servedLarvae = 0`），所以全巢看起來蛋白充足。
- `engine/brood.ts:45`：C4b 關閉時，幼蟲依**全巢**比例發育。2,417／3,168（76.3 %）個幼蟲日自己實付蛋白不到需求一半，卻以全速發育；30 個世界共化蛹 208 次。
- `engine/brood.ts:47`：幼蟲餓死依**全巢** `protein_gap_days`。2,669 個「自己蛋白缺口 ≥ 一半」的幼蟲日中，只有 3 日全巢缺口達到危險門檻；201 隻幼蟲曾連續 ≥ 5 日沒吃到蛋白，**沒有一隻因蛋白不足死亡**。
- `engine/brood.ts:27`：照護＝「全群當日開始時是否有任何工蟻」，不是個體被照顧。
- 打開 C4b（三種測試形式）時，發育改依自己的帳，平均 N ≈ 0.125；30 個世界只化蛹 1 次、羽化 0 次，保育工蟻日從 2,402 降到 1,968，無接觸的幼蟲日升到 87.5 %。三種形式的上游數字幾乎相同：瓶頸在上游，**不是形式造成**。C4b 形式照舊未選。

### 5.5 保育是否只用真實局部接觸【觀測】

靜態檢查各函式讀了哪些全巢量（`locality_audit`）：

| 函式 | 全巢量 | 說明 |
|---|---|---|
| `workers.ts selectTask` | 無 | 自己的訊號 |
| `workers.ts nurseContact` | 無 | v31 關閉時候選幼蟲是全群幼蟲名冊（位置未檢查，v31 修正） |
| `queen-feeding.ts nestRound` | `colony.stores.protein` | 工蟻只感知自己站的 store；一巢一 store，所以**等於**全巢蛋白存量（C3a 已陳述的等價） |
| `larva-feeding.ts broodLeg` | 無 | `here.length` 只是同地點均勻抽樣的分母 |
| `larva-feeding.ts larvaMetabolism` | 無 | 自己的帳 |
| `brood.ts developBrood` | `protein_gap_days`、`ratios.pFraction/sFraction` | **讀全巢量進個體發育與死亡**（L2／L3 已知缺陷） |

- 本報告程式本身是讀者：測試確認它不改所讀的狀態、所見狀態與純模擬逐位元組相同、不寫 `saves/`／`journal/`。

## 7. 限制

- 只有 Day0 實驗世界、60 日、兩季、三種建群；不涵蓋正式世界（Day14 預設 C4a 關閉）。
- cache 是單一總量：卸貨 → 取用的連結只能到「同一個池」，引擎沒有份量身分，報告不推斷個別份量來源。
- 巢內只有 store、queen、brood 三個命名地點與序數時間，不是幾何與物理接觸。
- 「嗉囊已滿」「cache 空」是依紀錄重播推得的原因，不是引擎事件欄位。
