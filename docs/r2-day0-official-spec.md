## 2. 架構提案：新正式世界由哪個引擎執行

### 2.1 #200 的硬性要求
1. Worker 與 Node **共用同一份**版本化的模擬規則與決定性核心，不得有兩套科學邏輯。
2. 畫面 FPS、動畫、視角與模擬時間步進解耦；UI 行為不改變正式事件。
3. 正式存檔含 schema／rules／species／environment 版本與指紋、初始條件與種子、模擬時刻、必要狀態、事件鏈承諾與校驗資訊。
4. 三種狀態：本機可玩／完整性檢查通過／Node 已重算驗證。
5. 逐位元一致只宣稱實際證明過的環境。

### 2.2 路徑 A（建議）：連續時間個體核心
```
               ┌───────────────────── engine/world/（新；純 TS，無 DOM／Node API）─────────────────────┐
               │ scheduler：engine/scheduler WorldScheduler（與 P0-A2 佇列合併；ID 壓縮；種子平手 #188 Q4）│
               │ environment：engine/clock（光照、天氣輸入→逐時溫濕度＋降雨事件；巢內微氣候代理）       │
               │ ecology：食源模組（事件驅動、帶來源 ID、不讀蟻群；沿用舊引擎的證據與參數，不搬程式）   │
               │ colony：P0-A2 個體行為＋局部守衛；蟻后（C3 路線）；幼體（P0-B 候選，Owner 選定）；死亡   │
               │ ledger：整數微份單一權威帳（#145）；人口 ID 流量                                         │
               │ adapters（保留介面，未接入）：physics shared-contract、CHEM sampleLocal                   │
               └───────────────────────────────────────────────────────────────────────────────────────┘
                     ▲ 同一份原始碼                                         ▲ 同一份原始碼
   瀏覽器 Worker（prototypes/continuous-world/worker 升格）        Node 驗證器（cli/，新）
   ・持續推進、快照、還原                                          ・讀存檔 → 檢查完整性 → 由受信任初始條件
   ・SAVE：IndexedDB、回復點、匯出入                                 與決定性輸入重算到存檔時刻 → 逐位元比對
   ・畫面只讀狀態框與事件                                           ・不符：標「未驗證」並保留診斷，不改存檔
```
- **優點**：本來就是連續時間、局部守衛、可切分不變、可快照；與 #189（運動學接入）、#190（決定性）、#200（Worker）的方向一致；物理與化學日後可在同一事件時間軸接入，不必再換時間模型。
- **代價**：蟻后、幼體發育、死亡、食源、天氣都要在新核心中重寫成事件驅動子模型；舊引擎的黃金測試不能直接沿用，要為新核心建新的基準。
- **要求**：舊引擎中「有證據的部分」（參數、文獻、候選模型）逐項移入，並在矩陣中改列；**缺陷不得一起搬過來**（G1～G9、#80、#84、#85、#9）。

### 2.3 路徑 B：把舊每日引擎包進 Worker
- Worker 以「每日」為事件單位執行 `engine/day.ts`，打開 C3a／C4a；Day0 由 `engine/initialization.ts` 產生；Node 驗證器重跑同一引擎。
- **優點**：生命史、食源、天氣、死亡、傷勢都已有程式與黃金測試，最快能呈現卵到成蟻的循環。
- **代價與風險**：
  - 360 分鐘時窗、沒有日夜（P0-A 尚未解決）；畫面只能在每日紀錄之間插值，與「看見螞蟻真實運動」不符。
  - G1～G9、#81 的全巢讀取違反 D3；在 C3b／C4b／C5 完成前，條件 2 不成立。
  - #84（同批同日羽化）、#80（食物無事件被刪除）、#85（對手固定拿走 22%）、#9（陣列順序）都要先修。
  - 舊引擎大量使用 `Math.*` 超越函數，跨環境逐位元一致要逐項稽核（#190 的同類問題）。
  - 物理與化學日後接入時，仍要換成連續時間；等於做兩次。

### 2.4 為什麼這是 Owner 的架構決策（O-1）

> **已裁示（2026-11-13，#212 Q1 A）**：採路徑 A。正式世界採 P0-A2 的連續時間、個體／事件驅動模型；瀏覽器 Worker 與 Node 重算驗證器共用同一套決定性核心；生命史以事件子模型逐步接入；舊每日引擎只供研究、資料與參數來源，不直接包成正式核心；不得把未實作機制假裝已模擬。以下為初版說明。
兩條路徑在技術上都能滿足 #200 的形式要求；差別在**哪些科學缺口先補**與**是否要做兩次時間模型轉換**。建議 A，因為 B 的主要缺陷（D3、日夜）正是 #201 條件 2 的核心。若 Owner 選 B，矩陣中 M10～M17 的阻擋原因改寫為舊引擎的缺陷清單，其餘不變。

### 2.5 決定性規則（兩條路徑都適用）
- 核心不用 `Math.random`、牆鐘或 `Math.*` 超越函數（改用 `engine/clock/detmath.ts` 或整數）；食物與能量用整數微份。
- 每個事件從由內容導出的具名亂數流抽樣（不用陣列位置）；同時刻事件依 layered 契約＋種子平手（#188 Q4，**標明是工程仲裁**）。
- `advanceTo(t)` 的結果與切分、速度、暫停、快照、追蹤無關（`tests/worker-runtime.test.ts` 的證明方法擴大到科學核心）。
- 不使用由鏡頭觸發的混合精度（#144）；背景生物若用群組精度，精度固定、不隨畫面改變。

## 5. 啟用後的版本邊界與 fork 政策（#201 條件 6、#200 第 5 項）

### 5.1 原則
1. **不回填**：規則更新只從一個明確的**版本邊界時刻** `t_b` 起生效；`t_b` 之前的事件與狀態永遠以舊規則重算，不改寫。
2. **每段歷史都可驗證**：一個世界的歷史是一串區段 `[t_0, t_1) @ v_1, [t_1, t_2) @ v_2, …`；Node 驗證器對每段用該段的規則版本重算。因此每個曾發佈的規則版本的核心原始碼都要保留（版本登錄檔＋封存分支），驗證器能載入任何已發佈版本。
3. **新模組從邊界起生效**：新接入的機制在 `t_b` 由明確、決定性、可稽核的初始化建立初始狀態（例如化學場在 `t_b` 為空），不得倒推「如果早就有這個機制」的狀態。
4. **玩家世界各自獨立**：每個玩家世界是自己的歷史；「正式」是指它從受信任的正式 Day0 起、在已發佈的規則版本下、可被 Node 重算驗證。

### 5.2 正式存檔必要欄位
`schema`、`schema_version`；`rules_version` 與 `rules_fingerprint`（核心原始碼＋參數）；`species_fingerprint`、`environment_fingerprint`（含天氣輸入來源）；`initial_conditions`（分巢單位抽樣分布、種子、情境、Day0 日期）與其雜湊；`segments`（每段的版本與邊界時刻）；`t_sim`、`seq`；完整狀態（個體、群體、環境、排程器、帳本；亂數為內容導出，不需保存串流狀態）；`event_chain`（每批事件的雜湊鏈頭）；`verification`（三種狀態之一＋驗證器版本＋平台）；`official`（只有 Owner 批准後的正式世界才可能為 true）。

> **2026-11-13 註**：存檔格式 v2（`docs/save-format-v2.md`）已實作其中一部分：`save_meta`（世界種類、受信任初始條件、物種／環境指紋、lineage）與事件鏈承諾 `chain`。與上列不同的是 **`verification` 不寫在檔案中**——驗證狀態只由驗證器的結果產生，檔案若自帶狀態欄位即被拒絕（較嚴格，採之）。尚缺：物種指紋（沒有正式物種檔）、分巢初始條件與 scenario checksum（2026-11-13：checksum 與決定性抽樣已定義，§4.8，但未寫入存檔）、`segments`（矩陣 M34、M37）。尚未模擬清單已加入 P0-A2 世界的 `save_meta.not_simulated`（M43，§10.4）。

### 5.3 舊存檔遇到新規則
| 情況 | 處理 |
|---|---|
| 只改 schema（不改行為） | 結構遷移登錄（已存在）；遷移後重新驗證，事件鏈不變 |
| 規則更新可從邊界接續 | 在 `t_b` 寫入 `rules_boundary` 事件（含新舊版本），新段從此起算；舊段仍以舊版本驗證 |
| 規則更新無法把狀態對應到新版本 | **fork**：建立新世界 ID，記錄父世界、分岔時刻與父版本；原世界保留、可繼續以舊版本遊玩（若執行環境仍保留舊版本）或只供觀看 |
| 執行環境不再提供舊版本 | 舊世界可匯出、可在 Node 驗證，但畫面標「規則不同，無法繼續」（現行行為） |

### 5.4 三種狀態
- **本機可玩**：存檔信封與雜湊有效，可在本機繼續；不宣稱已驗證。
- **完整性檢查通過**：結構、版本相容、資料有效性（範圍、守恆、ID 一致）通過；仍不是科學驗證。
- **Node 已重算驗證**：Node 驗證器從受信任初始條件重算，事件鏈與狀態逐位元相同，且該平台在 C4.4 的已證實清單內。
- **2026-11-13（#212 Q3 a、Q4 a）**：已證實清單＝x64 Linux／Node 22／Chromium。瀏覽器在任何平台都不顯示「Node 已重算驗證」；不提供未簽章的外部報告匯入；驗證器在可信執行環境（CI、維護者重跑）內直接重算的結果可用於正式驗收。ARM64、Safari、Firefox、實體手機可實驗性遊玩，標示未經 Node 重算驗證，不宣稱逐位元一致。
