## 1. 四種時間與換算（契約）
| 時間 | 表示 | 換算到排程器 | 誤差 |
|---|---|---|---|
| 世界時間 | `(day, minute)`；第 k 日＝`day0_date + k` 的臺灣民用日期（UTC+08:00，無日光節約）；分鐘就是當地鐘面時間 | #116 `checkTime`／`labelOf` | 標籤與精確時刻差 ≤ 30 µs（#117） |
| 生態事件時間 | 具名生態時鐘上的分鐘（`eco.light`、`eco.weather`、`eco.rain`），錨定在某日 00:00，另記**來源解析度**（日／時／分／秒／精確） | `ecoNative` → `exactOf`（無誤差） | 0；分鐘可超過 1440，精確地落到次日 |
| 物理事件時間 | 具名物理時鐘上的秒，錨定在某個世界時刻 | `physicsNative` → `exactOf`（無誤差） | 0 |
| 觀察器顯示時間 | 日期＋鐘面文字，**截斷**到事件的解析度，並附「真實時刻所在區間」 | 只由精確時刻導出，永不回饋 | 截斷是單調的：可能把兩個時刻印成同一時間，**不會反轉順序** |

- 排序完全交給排程器契約。`order` 是參數：本隔離時鐘**預設 `layered`**（Owner 2026-11-08 定為下一個隔離階段的目標契約）；`tick`（#116）保留為相容模式。兩種都測試。正式引擎（Day14、每日模擬）仍未使用任何一種。
- 只有日資料的值（例如未知時段的日雨量）解析度是「日」，顯示為「—」，不會被畫在某一分鐘。
- 民用日期以整數演算法換算（Hinnant days_from_civil），不用 `Date`。天文計算用的儒略日誤差約 10 µs，遠小於天文模型本身約 1 分鐘的誤差。

### 1.1 單一時間來源：同一時刻、不同時鐘
- 一個時刻的**身分**是它的精確時刻（#117 `ExactTime`）。分鐘、秒、生態時鐘、物理時鐘都只是它的「視圖」，換算（`exactOf`）沒有誤差。兩個事件同時，若且唯若精確時刻相同；沒有容許值、不看格點、不看顯示。
- 生產者要在**自己的時鐘**上表示「與某事件同一時刻」時，用 `nativeOnClock(精確時刻, 時鐘, 單位, 錨點)`：回傳的值換算回去**逐位元**等於該時刻，否則拒絕（`requireNativeOnClock` 丟出錯誤）。**絕不回傳鄰近的時刻**，所以浮點換算不會製造假的先後。
  - 例：06:00 + 30 s（秒時鐘）與 360.5 min（分鐘時鐘）是同一時刻；14:07:15（847.25 min）可以在三個時鐘上精確表示。
  - 反例：1.5 s 與 0.025 min 在二進位是兩個不同時刻；06:00:40 在分鐘時鐘上沒有精確值（40/60 不可表示）——要求時被拒絕，而天真的 `360 + 40/60` 會變成另一個時刻（測試證明它不會被當成同時）。
- 測試：6000 個隨機原生時間，原生 → 精確 → 同一時鐘逐位元相同；換到其他時鐘時，要嘛是同一精確時刻、要嘛拒絕，錯誤數 0；換回原時鐘得到原值。
- `minutesOfDay`、`secondsOfDay` 只是給報告或物理輸入的數字視圖（誤差 ≤ 1 ulp），**不用於排序**。

## 2. 跨午夜與日結算
- **24:00 不重設任何東西**：光照狀態、正在下的雨、尚未執行的事件都延續到次日。氣溫的夜間段是從日落到次日最低溫的**同一段函數**，濕度的實際水氣壓在相鄰兩日 12:00 之間線性內插，兩者在 24:00 連續（測試）。
- 日結算＝排程器 `runDay(d)`：處理第 d 日剩下的事件、關閉該日（之後不能在該日排入事件，也不能重跑），再做守恆檢查。被 `runUntil` 或快照切開的一天，仍以同一天結算（每日計數存在環境狀態中）。
- 降雨事件跨午夜時是**一個**事件（Owner 2026-11-03 決定）；它的雨量分成兩段，各自算進當日的日雨量。

## 3. 光照（一般方法，非生物參數）
- NOAA 太陽計算式（R390，依 Meeus）。日出／日落：太陽高度 −0.833°；民用曙暮光：−6°。在事件時刻本身迭代求解，計算出的時刻上太陽高度與門檻差 < 1×10⁻⁶°。
- 代表點：北緯 24.17°、東經 120.64°（西屯區約略值，**示意**；花園是虛構的，沒有量測座標）。經緯度各移 0.1°，日出日落最多移動 0.4 分鐘。
- 地形、建築、樹蔭與實際折射不模擬。NOAA 說明的準確度：±72° 緯度內約 1 分鐘。

## 4. 天氣輸入與標示
依 `docs/weather-data-policy.md`：
- 每日輸入必須標明 `observation`（測站代號）、`forecast`（發布時刻與有效時段）或 `synthetic_climatology`（`synthetic: true`、`assumption: true`、產生器名稱與亂數流）。混淆就拒絕：觀測不得標合成、合成不得冒充逐時觀測、預報不得當實測。
- 缺值保持 `null`：日雨量 `null` 時不產生事件，`raining` 為 `null`（未知），**不當作 0 mm**。
- Day0 實驗世界的日資料來自引擎既有的合成氣候（`engine/weather.ts` `calcWeather`，臺中 1991～2020 月平均），只讀世界的種子與氣候記憶，不讀蟻群。全部 `synthetic: true`。
- 逐時取樣：預設每 60 分鐘一個 `weather_sample` 事件（可設任何整除 1440 的間隔）；每筆記錄氣溫、濕度的值與來源（逐時觀測／由日資料重建／無法取得及原因）。
- 降雨：`rain_start`、`rain_end` 事件。逐時觀測的雨以「小時」為解析度；只有日雨量時，必須由呼叫者提供標示為遊戲假設的時段情境，才會抽出事件。

| 項目 | 方法 | 分類 |
|---|---|---|
| 日內氣溫形狀 | Parton–Logan 型：白天正弦、夜間指數衰減（R247，只核對書目）。本實作的參數化（高峰在太陽正午後 a 小時、最低在日出後 c 小時、夜間段重新縮放使其恰好接到次日最低溫）是**本實作的選擇**，可能與原文不同 | 方法：一般方法；**係數 `null`**：沒有係數就不產生逐時氣溫 |
| 飽和水氣壓 | FAO-56 式 11：e°(T) = 0.6108 exp(17.27T/(T+237.3)) kPa（R391；以原文例題 e°(24.5 °C) = 3.075 kPa 驗證） | 一般物理 |
| 實際水氣壓 | 由日平均 RH 與日平均溫推得，在相鄰兩日 12:00 間線性內插；RH 上限 100% | 遊戲假設 |
| 合成降雨時段 | 事件數、長度分布 | 遊戲假設；**預設 `null`**（不發明時段） |
| 雨量分配 | 整數 nm（10⁻⁶ mm）、最大餘數法；與 #42 的參考實作逐一相同 | 算術 |

## 5. 不變量（全部由測試檢查）
1. **單調時鐘**：執行紀錄的精確時刻與世界標籤都不遞減；顯示鍵不遞減；環境事件在兩種契約下都沒有合併或反序。
2. **恰好一次**：每個事件恰好執行一次（`audit`、`verifyLog`）；關閉的日不能重跑。
3. **降雨守恆**：每日各事件落在該日的雨量加總**恰好**等於該日雨量（整數 nm；40 個種子 × 8 日，含 36 次跨午夜與 86 次截斷）；事件分段分鐘數等於事件長度。次日預算不足、未知或超出時間範圍時截斷並記錄，不靜默丟棄。逐時與日雨量不一致時記錄，不掩蓋。
4. **光照**：每日 曙光 < 日出 < 正午 < 日落 < 暮光；每天依序轉換一次；每日在夜間結算。
5. **氣溫／濕度**（以 27 組係數的格點檢查，這些係數只是測試用，不是參數值）：恰好達到日最低與最高溫；在最低點、日落與 24:00 連續；在相鄰日極值之間；夜間單調下降；RH 在 (0, 100]。
6. **快照／還原**：在 13:37、00:00、雨中切開並還原，結果與連續執行逐字相同；不能在另一種契約下還原。
7. **排列與種子**：排入順序打亂 5 次，紀錄相同；光照與氣溫事件與種子無關；換種子會移動合成雨的時段，但日總量不變；重播相同。
8. **四種時間共用一條時間軸**：錨定在 23:00、跨越午夜的物理秒事件與生態分鐘事件依精確時刻交錯，標籤與顯示都不反轉順序。
9. **隔離**：正式程式（`engine/*.ts`、`cli/`、`web/src`、排程器、物理層）都不匯入 `engine/clock`；它不在規則指紋內；它只匯入排程器、亂數與自己的模組；程式碼不提到任何蟻群端狀態；不用 `Math.random`、`Date`、平臺 API；黃金測試逐位元組相同。

## 6. 哪些是模型假設
- 代表點座標（示意）、取樣間隔、濕度的水氣壓內插、雨量在事件內均勻分布、合成降雨時段（若提供）：遊戲假設。
- 日出日落與氣溫形狀：一般方法；形狀係數 `null`。沒有內建預設值（`TEMPERATURE_SHAPE_DEFAULT = null`）；缺任一係數的形狀被拒絕、不補值；係數 `null` 時每個取樣的 `temp_c`、`rh_percent` 都是 `null`（來源 `unavailable`，附原因），環境狀態也是 `null`（`tests/p0a1-24h-clock.test.ts` §7 釘住）。
- 日資料本身：Day0 實驗世界中全部是合成氣候（`synthetic: true`），不是 2027 年的天氣。
- 微地點溫度（地表、日照、遮蔭）、巢內溫度、雨後地表潮濕時間：**本 PR 沒有做**。

## 7. 多蟻群共用一條世界時間軸（Issue #9 選項 A；隔離實驗）
- 所有蟻群的事件都是同一個排程器上的根事件，各用自己的原生時鐘（例：A 是錨定 06:00 的秒時鐘、B 是錨定 00:00 的分鐘時鐘、C 是錨定 05:30 的秒時鐘），與環境事件（光照、取樣）交錯。**不會先跑完 A 的一天再跑 B。**
- 每一批（同一精確時刻、同一 round）以**一個集合**交給生物／資源模型（`ClockRun.foreign`），時鐘與排程器都不選贏家。
- **環境與排程器同時提交（Codex R13-02）**：契約與反例見 §7a。
- 同一資源、同一精確時刻的抵達＝同時競爭。實驗觀察器只記錄一個明確的 `contest_unresolved` 事件（下一 round、同一時刻）：參與者是集合、`resolution: 'unresolved'`、`rule: null`、沒有 `winner`。**沒有**依陣列順序、ID、平分或隨機輪替決定；沒有消耗任何食物。競爭規則需要 Owner 或文獻決定。
- `cause` 欄位必須指向批次中的一個事件，所以取參與者中 ID 最小者——這只是標籤，不是贏家。
- 測試（3 群、9 隻、2 個資源、233 次抵達，跨午夜）：
  - 抵達依精確時刻執行，蟻群之間切換 100 次以上；
  - `colonies[]` 順序（4 種）、排入順序打亂、所有 ID（蟻群、工蟻、資源、時鐘）改名：結果完全相同；
  - 秒時鐘 A 與分鐘時鐘 B 同時到 R1 → 一個雙方競爭；三群同時到 R2 → 一個三方競爭；同時刻但不同資源 → 不是競爭；
  - 近乎同時（無法精確表示）的一對：`layered` 下是兩個時刻；`tick` 下被併入同一格並**回報合併**，模型仍不把它當成競爭；
  - 兩種契約、在 06:00:30、00:00、14:07 快照／還原都等於連續執行；每個事件恰好一次。
- 這只是時間軸與交接介面，不是行為模型；`shared-resource.ts` 放在 `prototypes/`，不在 `engine/`。

## 7a. 提交原子性：契約與反例（Codex R13-02；Owner #125 審查）
ccd9aad 用通用的 `WorldScheduler.setCommitHook(fn)`：鉤子在排程器提交**之前**執行任意程式碼；鉤子若先改了外部狀態再丟錯，排程器的復原碰不到那些外部狀態。「請鉤子自律只做最後一次指派」不是 API 保證。現已移除此鉤子，改為兩階段的 `CommitCell`。

**保證的範圍（只有這些）**
- 排程器狀態＋已附掛的 `CommitCell` 值：每一批要嘛排程器提交且每個回傳 `{ value }` 的 cell 換成該值，要嘛（處理函式、輸出驗證、任一 `prepare`、重入被拒時丟錯）排程器與**所有** cell 都不變。
- 換值由排程器在自己（不會失敗）的提交之後做私有欄位指派；換值時不執行 getter、Proxy trap 或任何呼叫者程式碼。`prepare` 的回傳只接受純物件、唯一的資料屬性 `value`，在第一階段讀一次。
- `ClockRun` 擁有的狀態：環境狀態（私有 cell，深度凍結，只能被換掉、不能被改）與已結算日（凍結陣列）。處理函式在副本上計算並凍結；cell 的 `prepare` 只檢查、不寫入；`closeDay` 的檢查都在寫入之前，寫入只有兩次指派（唯一可能被拒的 `replace` 先做）。`handler`、`state`、`days` 都不能從外部替換；暫存欄位是私有的。
- 環境事件只能由 `ClockRun.handler` 執行；用其他處理函式（含包一層再呼叫它）推進排程器會被拒絕，否則排程器前進、環境卻沒跟上。

**明確不保證**
- `prepare`、處理函式或 `foreign` 寫到 cell 以外的東西（其他物件、閉包、另一個排程器、另一個排程器的 cell），批次失敗時**不復原**、重試時**不去重**。`prepare` 必須沒有副作用，但排程器無法強制。cell 的值以參照儲存、不複製也不凍結，由 cell 的擁有者負責（`ClockRun` 會凍結）。
- cell 不在快照中；還原後由擁有者重新附掛（`ClockRun` 指派 `scheduler` 時自動移動；移動的所有檢查在任何改變之前）。
