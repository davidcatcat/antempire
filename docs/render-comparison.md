# 大量螞蟻繪圖：三種方式對照與正式畫面效能重測（Issue #159，Owner 決策 24、25）

> 本文只談**繪圖**。畫得快慢不代表模擬能力；渲染不改變任何位置、時間或事件；視野裁切只影響繪圖。合成壓力測試的位置是**示意**（不是引擎資料），只用來量「畫 N 個物件」的成本。所有數字來自 headless Chromium（軟體繪圖、SwiftShader 軟體 GL）與**共用主機**，不是實機。

## 1. 比較對象與作法

| 代號 | 內容 | 程式 |
|---|---|---|
| A | 現有 Canvas 2D：每隻螞蟻一次「平移＋旋轉＋貼圖」 | `web/src/render-canvas.ts`（預設） |
| B | Canvas 2D＋**預旋轉圖集**：走路 12 格＋停止 8 格，每格烘成 n 個朝向（2π/n），5 種體色各一組＋共用陰影一組，依 DPR 烘焙；畫時只做軸對齊貼圖 | `LayeredRenderer(canvas, { antSprites: 'prerotated' })`；純函式規劃在 `web/src/render-scene.ts`（`planRotatedAtlas` 等） |
| C | PixiJS 8.22.0（WebGL）批次精靈畫兩個螞蟻圖層；其他圖層仍由同一個 LayeredRenderer 畫，螞蟻以上的圖層畫在透明的上層 2D 畫布，11 層順序不變 | `prototypes/render-compare/src/pixi-ants.ts`（沿用 #102／#113 `prototypes/render-bench` 的作法與鎖定版本；本機 bundle，不連 CDN） |

- **同一份資料、動畫、鏡頭**：比較頁 `prototypes/render-compare/`。`replay`＝實驗世界 A1 的真實重播（位置＝`game-model.antFrame`＝`model.poseAt`，遊戲畫面的放大規則、體色變化、轉向顯示）；`stress100／1000／5000`＝合成示意位置（60 cm 視野，最小 26 px）。動畫以**固定步長**（1/60 s）前進，所以第 k 幀在 A、B、C 的輸入完全相同；每次執行都比對輸入雜湊（全部相同＝渲染不回饋到動畫）。
- **固定畫質 1**（不畫反光，其餘全開；DPR 上限 2），避免自動降畫質讓三者在不同畫質比較。
- **量測**：每組合 3 輪交錯（A B C A B C …），取中位數；每輪暖機 4 秒、記錄 6 秒。FPS／p95／p99＝相鄰 rAF 間隔；主執行緒 ms＝`performance.now()` 包住整幀繪製，以及兩個螞蟻圖層；renderer／GPU 行程 CPU＝CDP `SystemInfo.getProcessInfo` 差值÷幀數（SwiftShader 下 GPU 工作就在 GPU 行程的 CPU 上，所以這是「GPU 成本」的代理值）；JS heap＝`performance.memory`；螞蟻材質＝圖集畫布的 RGBA 位元組估計。
- **GPU 計時**：`EXT_disjoint_timer_query_webgl2` 在此環境**不可用**；未做 Chrome tracing。GPU 成本只有上述行程 CPU 代理值。
- 設定檔：desktop 1280×800 DPR 1；Pixel 7＝Playwright 裝置模擬（畫布 824×1678，DPR 上限 2）；Pixel 7＋CPU 4× 降速（Chromium 只降速 renderer 主執行緒，**不降速 GPU 行程**——這對 C 有利，見 §5）。
- 主機：4 核心，量測期間有其他工作，load average 2.5～12（每列記錄於 `results.json`）。絕對 FPS 因此偏低且有波動；同組合三者交錯量測，**相對比較**較可信。

## 3. 預旋轉圖集的記憶體與速度限制（B）

- 記憶體＝(畫出長度×DPR)² × n × 20 格 × (5 體色＋1 陰影)。例：26 px、DPR 1、n＝16 → 11.3 MB；48 px、DPR 2 → 即使 n＝8 也要 64 MB；遊戲畫面的放大螞蟻（64–67 px、DPR 2）n＝8 要 137 MB。
- **速度也受記憶體限制**：Chromium 的 Canvas 只有在來源圖的總量留在影像快取內時，貼圖才便宜。微基準（同頁 1000 次貼圖）：512² 小圖少量時約 1 ms，1024² 以上的單張或總量 ≥ 約 24 MB 時升到 20–50 ms，比 A 的旋轉貼圖（約 25 ms）還慢；第一版用 2048×4096 圖頁時 B 反而比 A 慢 2–4 倍。因此預設**圖頁 512²、總預算 16 MB**（工程限制，非模型數值），超過預算就整組退回 A。
- 只預旋轉走路與停止；轉向動作（只在紀錄的方向改變時短暫出現）仍用 A 的即時旋轉。
- **未來頭部／觸角顯示狀態**：`planRotatedAtlas(…, poses)` 有可插拔的第三軸，每多一種姿勢，記憶體線性增加（測試驗證），在同一預算下 n 會變小（例：26 px、DPR 1，4 種姿勢 → n 由 16 降到 < 16）。若平行 PR 加入頭部偏轉＋左右觸角獨立狀態（例如 3×3×3＝27 種），預旋轉的組合數會爆炸，B 只在極小尺寸可行；這類逐隻狀態較適合即時旋轉（A）或 GPU（C）。

## 5. 解讀限制

1. SwiftShader 把 WebGL 放在 CPU 上：C 的「GPU 行程 CPU」在 1,000 個物件時約 115–290 ms/幀，是本環境 C 變慢的主因；真 GPU 上這部分可能小一到兩個數量級，**排名可能相反**，但本環境無法證明。
2. CPU 4× 降速只降 renderer 主執行緒，不降 GPU 行程，所以 4× 下 C 在 1,000／5,000 個物件勝出（4.1 對 2.3；1.1 對 0.3 fps），部分是模擬方式造成的偏差。
3. Pixel 7 只是視窗與 DPR 的模擬，CPU／GPU 是同一台主機。
4. 共用主機負載 2.5–12，絕對值偏低；同組合交錯量測三輪取中位數以減少偏差。
5. 5,000 個物件時 Canvas 2D 的螞蟻圖層成本超線性（desktop A：1,000 個約 15 ms → 5,000 個約 590 ms），原因未查明（推測為 Chromium 畫布命令緩衝與影像快取），三種方式在此規模都遠低於目標。

## 6. 建議（依數據，低成本優先）

1. **正式遊戲畫面維持 A（Canvas 2D）**。目前重播只有約 10 隻螞蟻，螞蟻圖層每幀 < 2 ms，瓶頸不在螞蟻繪圖；B 在遊戲放大倍率下超出預算（自動退回 A），C 在本環境更慢（desktop 重播 34.9 對 43.3 fps）。
2. **B 保留為選項，不預設開啟**。它在 DPR 1 的大量螞蟻有效（desktop 1,000 個：螞蟻圖層 15.0 → 4.9 ms，FPS 中位數 12.2 → 15.4，60 秒 13.4–14.8 → 17.8–21.8；5,000 個 591 → 369 ms），但 DPR 2 時 5 種體色放不進 16 MB；朝向誤差最多 180°/n（n＝16 為 11.25°），而且頭部／觸角狀態加入後組合數會再乘上去。若日後真的有上千隻的畫面，可考慮「大量時在 DPR 1、單一體色」使用 B——這是畫面上的取捨，需 Owner 決定。
3. **目前不切換 WebGL**。C 把主執行緒成本降了 5–40 倍（1,000 個 2.7 對 15 ms；5,000 個 15 對 591 ms），顯示在真 GPU 上大規模時可能明顯更好；但本環境只能看到軟體 GL 的代價。切換前要：(a) 在真實手機與桌機 GPU 上重跑本比較頁（`node bench.cjs` 可連真裝置或手動開頁）；(b) 引擎真的輸出上千個需要畫的個體；(c) WebGL 失敗時自動退回 Canvas 2D；(d) 接受約 570 KB 的相依與維護成本。
4. 4× 降速仍在 30 邊緣：下一步應查「非螞蟻」的成本（地面分塊烘焙與首幀、DPR 切換時的重烘），不是螞蟻繪圖方式。
